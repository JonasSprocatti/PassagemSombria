# Passagem Sombria — Deck de Campo Online

Mesa virtual (VTT) para o RPG espacial *Passagem Sombria*. SPA estática em **JavaScript puro (ES modules)**, sem build. Backend: **Supabase** (Auth + Postgres + Realtime + Storage). Hospedagem: Vercel (site estático, raiz = `public/`). PT-BR em toda a UI, comentários e nomes.

## Como rodar

Precisa ser servido por HTTP (usa ES modules nativos — `file://` não funciona).

```
cd public
python -m http.server 3000   # abre http://localhost:3000
```

Antes: preencher `public/js/config.js` com `SUPABASE_URL` e `SUPABASE_ANON_KEY` (não versionado / placeholders). Segurança real fica na RLS do Supabase, não no front.

**Nesta máquina de dev (Windows), rodar comandos de shell via PowerShell, não Bash**: o Bash embutido falha ao dar fork (`dofork: child -1 - forked process ... died unexpectedly`, `Resource temporarily unavailable`) de forma consistente neste ambiente — todo comando simples (`git status`, `wc -l`) morre. Usar a ferramenta PowerShell para git/testes/etc. aqui.

**Este ambiente de dev (o Claude Code que edita este repo) não tem Node.js instalado** — `node --check`/`node --test` não rodam localmente aqui (`node` não é reconhecido pelo PowerShell). Não tentar rodar Node nesta máquina; revisar sintaxe manualmente e deixar `tests/*.test.js` para o CI (`.github/workflows/testes.yml`, roda a cada push/PR) confirmar.

Não há lint. Há um início de testes automatizados em `tests/` (ver seção **Testes automatizados** mais abaixo) cobrindo as funções puras de `dados-jogo.js` — o resto da verificação ainda é manual no navegador (com um projeto Supabase configurado).

### Modularização de `telaMesa` (concluída)

`telaMesa` era ~3200 linhas, a maior e mais frágil função do app (chat + ficha do jogador + combate pessoal + campo tático + combate espacial + ferramentas do Mestre, tudo numa closure só, com um `render()` que desenha todas as abas de uma vez). Sendo dividida em arquivos por fatia de funcionalidade, seguindo um plano registrado (histórico da sessão que fez o Passo 0 e a 1ª extração):

- **Passo 0 (concluído)**: promoveu 14 `let`s soltos da closure (`souMestre`, `modoJogador`, `meuPers`, `tokenSel`, `campoZoom`, `pintarMsg`, `mapaCtrl`, `abaMesa`, `timerInt`, `vantagem`, `privada`, `asCegas`, `recapFeita`, `gravandoAte`) para um único objeto `ui`, criado uma vez por chamada de `telaMesa(id)` — necessário porque closures não atravessam módulos, então estado mutável compartilhado entre fatias precisa viver numa referência estável.
- **`mesa-mestre.js` (concluído)**: exporta `abrirMestre(ctx)` — o overlay inteiro do `#abrir-mestre` (🎛 Tela do Mestre: Mesa/Referência/Tabelas/Encontros/Facções/Contratos/Linha do tempo/Anotações), incluindo `fazerBackup`/`restaurarBackup` que só eram usados ali. `ctx` hoje é só `{ id, camp, pers, enviar, salvarCamp, render }` — o subconjunto do objeto `ctx` completo (ver histórico) que esta fatia realmente usa; não precisou de `ui` nem de `k`/`f`. `app.js` ganhou `export` em `esc` (já tinha), `combateVazio`, `naveTaticaVazia`, `rolarTabela`, `orcamentoEncontro`, `sugerirEncontro`, `PESO_AMEACA` especificamente para isso, mesmo padrão de `biblioteca.js`/`admin.js` (corpo copiado tal e qual, só os identificadores livres viraram imports).
- **`mesa-nave.js` (concluído)**: exporta `renderNave(ctx)` (HTML da aba Nave, interpolado no template de `render()`) e `wireNave(ctx)` (todos os handlers da aba: `#def-nave`, `#sel-posto`, `#cbn-*`, `[data-cbn-rm]`, `[data-cbn-atk]`, `[data-av-fix]`, `#nave-repar`, `#nave-upg`, `#nave-hit` e as ações de posto `[data-est]`). Diferente do `mesa-mestre.js` (carregado só no clique), este é carregado no topo de todo `render()` via `await import("./mesa-nave.js")` — o HTML da aba precisa sair síncrono dentro do template, e `import()` repetido é gratuito (cache de módulo do navegador). Não é import estático no topo de `app.js` de propósito: evita import circular estático (`mesa-nave.js` importa de volta de `app.js`), mantendo o padrão do resto do app. `ctxNave` montado em `render()` logo antes do `shell("mesa", …)`: `{ id, camp, pers, membros, ui, f, k, nave, cbn, meuPosto, enviar, salvarCamp, salvarCbn, render, defesaNaveParty, bonusDefVeiculo }`. `salvarCbn` subiu pro setup de `telaMesa` (junto de `salvarCombate`). Ganharam `export` em `app.js`: `POSTOS_ORDEM`, `combateNaveVazio`, `defesaNave`, `danoNave`, `rolarAvaria`, `ataqueDaNave`, `ehNave`, `foraDeCombate`, `salvarFicha`. Dependência cruzada que continua valendo: `[data-est]` escreve `camp.combate.nave` (`manobraExtra`/`dobra`/`evasiva`), que o HUD da aba Combate lê — `[data-av-fix2]` e o HUD da nave em cena ficaram em `app.js` (são da fatia de combate). `#cbn-iniciar` já era handler morto (nenhum botão renderiza esse id) e veio junto sem mudança.

Última fatia; ver essa mesma linha da tabela para o que foi movido vs. o que ganhou só `export`.
- **Com as 4 fatias prontas**, `telaMesa` em `app.js` ficou só o "cimento": setup da closure (`ui`, `camp`/`pers`/`membros` carregados do Supabase, helpers compartilhados como `aplicarDanoAlvo`/`habsDoCombatente`/`aurasAtivas`/`gastarAcao`/`sincronizarCdCombate`/`minhaLinhaCb`/`aurasSobre`, todos precisam continuar em `app.js` porque mais de uma fatia os usa), o roteador de abas (`data-mesa-aba`), o chat/mensagens/realtime, e a montagem dos 4 objetos `ctx*` + as chamadas `render*(ctx*)`/`wire*(ctx*)` de cada fatia a cada `render()`. `app.js` caiu de ~4180 para ~2390 linhas nessa modularização inteira (as 4 fatias somadas). ## Modelo de dados

- **`f`** = objeto `dados` do personagem (JSONB em `personagens.dados`). Shape canônico em `novaFichaDados()`. Sempre mesclar sobre ele: `{ ...novaFichaDados(), ...(row.dados||{}) }`.
- **`k = calc(f)`** = derivados recalculados a cada render; nunca persistido. `k.efeitos` é a instância `FichaEfeitos` (motor declarativo).
- **`dcSalvaguarda(k, atributo)`** = `8 + mod` — CD de teste de resistência forçado por **habilidade** de personagem (`salvaguarda`). Palavras-chave de arma e granadas usam o `cd` **fixo do texto** (13 físico / 14 Acrobacia); granadas com `pericia` (Acrobacia) rolam `d20 + attr + perícia`.
- **`aplicarCond(alvo, cond, turnos)`** (módulo) — aplica condição no rastreador com a regra da mesa: **dano contínuo** (Sangrando/Em chamas/Envenenado) empilha **+1 turno** se já ativa (nunca aumenta o dado, sempre 1d4/1d6/1d4 fixo); **estado** renova para a maior duração. Guarda `turnos+1` para condições de estado porque o `#cb-prox` decrementa no início do turno do afetado antes dele agir. Padrão de duração: hard (Atordoado/Paralisado/Congelado) 1t · estado (Cego/Caído/Marcado/Lento/Amedrontado/Enfraquecido/Silenciado) 2t · dano 3t.
- **Condições no fluxo de ataque** (`[data-atq]`): atacante **Cego/Amedrontado/Envenenado** → Desvantagem; **Enfraquecido** → `danoFinal × 0.5`; **Atordoado/Paralisado** (não-Mestre) → bloqueio via `minhaTrava()`. Alvo **Marcado** → +2 acerto de quem o ataca; alvo **Atordoado/Paralisado/Caído/Cego** → Vantagem contra ele. Vant/desv de todas as fontes somam e reduzem a −1/0/+1. `#conjurar` e `[data-hab-usar]` também respeitam `minhaTrava(["silenciado"])`. **Paralisado a até 2m** é Crítico automático (não só Vantagem) — `paralisadoPerto`/`multCrit` em `[data-atq]` e `paralisadoPerto2`/`critAuto2` em `.cb-atk`; nat 1 ainda falha. Já foi bug real: só dava Vantagem, igual às outras condições do grupo `alvoAberto`, sem o multiplicador que o texto da condição promete.
- **Movimento no campo tático × condições**: Paralisado/Congelado/**Lento** bloqueiam o movimento por completo (deslocamento zero); só **Caído** (ou ter tentado **Apagar fogo** no próprio turno, `c._movMetade === rodada`) reduz a deslocamento à metade. Já foi bug real: Lento estava agrupado com Caído (metade do deslocamento) em vez de "perde a Ação de Movimento" (zero) — checar em `.cb-token.movivel` → `pointerdown`.
- **Mecânicas de condição que exigiam ação do jogador** (`.acoes-mesa`, aba "Meu personagem", só aparecem em combate ativo e com a condição presente):
  - **🔥 Apagar fogo** (`#cb-apagar-fogo`): gasta Ação Principal **e** Reação (duas chamadas a `gastarAcao`), marca `linha._movMetade = rodada` (deslocamento pela metade neste turno, limpo no `#cb-prox` seguinte), rola **d20 puro sem modificador** — ≥10 remove "Em chamas" na hora, <10 continua queimando (mas as ações já foram gastas).
  - **🧎 Levantar** (`#cb-levantar`): gasta Ação Principal **e** Ação de Movimento, remove "Caído" na hora, sem rolagem.
  - Os dois respeitam o mesmo gate de turno do `[data-atq]` (não-Mestre só usa no próprio turno) e `minhaTrava()`.
- **Desvantagem de condição em testes de perícia** (fora de ataque): `desvPorTeste(condsList, pericia)` em `telaMesa` — **Cego** só atrapalha testes visuais (`PERICIAS_VISUAIS`: Percepção, Investigação, Prestidigitação, Pilotagem); **Envenenado** só testes físicos (`PERICIAS_FISICAS`: Atletismo, Acrobacia, Furtividade). Usado em `#rolar-per` e nos dois lados do `#teste-oposto` (`rolarEEnviar` ganhou um 4º parâmetro `vantOverride` pra isso). Fora dessas listas, a condição não pesa no teste — é intencional (não é geral, só onde faz sentido narrativo).
- **Amedrontado com fonte rastreada**: `aplicarCond(alvo, cond, turnos, origemId)` — 4º parâmetro opcional, guardado como `cond.origemId` na linha do rastreador. Preenchido pelas 3 rotas que hoje aplicam Amedrontado no atacante real: `aplicarEmAlvos` (salvaguardas/scripts/granadas, usa `minhaLinhaCb()?.id`), o gatilho `ao_acertar` de criatura em `.cb-atk` (usa `c.id`), e `aplicarCondsNoAlvo` de palavra-chave/munição em `[data-atq]` (usa `minhaLinhaCb()?.id`). Com `origemId` conhecido: a Desvantagem em `[data-atq]` só vale atacando essa fonte (`desvPorMedo`), e o bloqueio de aproximação no campo tático (`.cb-token.movivel`) mede a distância só até ela, não até "qualquer inimigo". Sem `origemId` (condição aplicada por uma rota antiga que não foi atualizada, ex. o Mestre aplicando manualmente por `.cb-cond-add`) cai no comportamento antigo — vale contra/para qualquer inimigo, pra não enfraquecer a condição silenciosamente.
- **`aplicarDanoAlvo(alvo, valor)`** (helper em `telaMesa`) = ponto único de todo dano ROLADO contra um combatente. Ordem: couraça por limiar de criatura (`habs` com `imunidade.limiar`) → redução de dano do alvo (`k.efeitos.aoSofrer().reducao`, jogador) → corpo (`sincronizarFicha`). Nave → `danoNave` + persiste `camp.nave` se `nave_party`. Os botões `±5` / definir HP do Mestre NÃO passam por aqui (ajuste livre). Usado por `.m-aplicar`, blocos `alvoNave`/`alvoCombatente` do `[data-atq]` e `aplicarEmAlvos`.
- **`c.cd` do jogador no rastreador é uma FOTO**, tirada uma vez em `#cb-iniciar` (`cd: kk.cd`) — não recalcula sozinha depois. `sincronizarCdCombate(personagemId, dadosFicha)` (helper em `telaMesa`, perto de `salvarCombate`) recomputa `calc(dados).cd` e atualiza a linha se mudou; chamado nos 4 pontos onde `f.modos`/`f.modosAte` mudam em combate: ativar modo/criar (Criogénese, Endurecer…), Êxtase da Batalha (`tipo:"tabela"`), ligar/desligar o gás do Ven'y, e a expiração automática de modos no `#cb-prox`. Sem isso, um jogador que ativa Criogénese (Escudo de gelo, +2 Defesa) **em pleno combate** segue tomando dano como se a CD não tivesse mudado, porque `.cb-atk`/`[data-atq]`/`aplicarEmAlvos` checam `alvo.cd` da linha, não recalculam do zero. Já foi bug real — CD do Urak ficou 2 pontos abaixo do esperado depois de criar o escudo em combate.
- **`defesaNaveParty()`** = `10 + manobra + bonusDefVeiculo()`, onde `bonusDefVeiculo()` soma `efeitos.defesaVeiculo()` do personagem do piloto no leme (Instinto Evasivo). Usado no painel de combate, aba nave e Manobra Evasiva.
- **Implantes inertes (Zona Morta)**: `calc(f, { semImplantes: true })` recalcula a ficha inteira como se a pessoa não tivesse implante nenhum — some o +2 de RAM do Chip, o +1 de CD das Placas, a carga de Cinético e todo efeito declarado de implante; marca `k.implantesInertes`. `telaMesa.render()` passa `semImplantes: auraNega("implantes")` (a própria pessoa) e `aplicarDanoAlvo` passa `auraNega("implantes", alvo)` (para a redução de dano do alvo também cair). Fora de combate, ou fora do raio, nada muda.
- **`aurasAtivas()` / `auraNega(oque)`** = auras de criatura (`hab.gatilho === "aura"`) das criaturas vivas no rastreador. Sem posição, valem para todo o combate. `auraNega("tecnomancia")` bloqueia `#conjurar`; `auraNega("cura")` bloqueia `#enviar-cura`. Banner no painel de combate lista todas. **`#cb-add-btn` copia `b.habs` para a linha do combate** — sem isso, auras, couraça por limiar (`aplicarDanoAlvo`) e efeitos automáticos de criatura (`#cb-prox`) não funcionavam para bicho do bestiário. Criaturas com aura: `Silenciador Cósmico` (nega tecnomancia+implantes), `A Ferida do Mundo` (nega cura+tecnomancia+implantes).
- **`modosAtivosDe(f)`** lê efeitos de modo em `h.opcoes`/`h.resolve.opcoes` (gás Ven'y, Êxtase) **e** em `h.resolve.efeitos` (Endurecer — modo sem opções). Sem esse último, Endurecer não reduzia dano.
- **Ataque de jogador em combate**: não-Mestre só ataca no próprio turno (bloqueio; o Mestre rola pelo ⚔ da linha dele). Com alvo escolhido, o seletor abre já com um inimigo selecionado; "sem alvo" é a última opção (para atacar algo fora do rastreador).
- **Modo Jogador** (`#modo-jogador`, só para `ehMestreReal`): toggle no topo da mesa que zera `ui.souMestre` (guardado em `localStorage` `ps-modojog-<id>`) para o Mestre testar/jogar como tripulante — some as ferramentas de Mestre e valem os bloqueios (turno, Atordoado). `ehMestreReal` guarda a permissão verdadeira.
- **Objeto `ui` em `telaMesa`** — Passo 0 da modularização (ver plano). `souMestre`, `modoJogador`, `meuPers`, `tokenSel`, `campoZoom`, `pintarMsg`, `mapaCtrl`, `abaMesa`, `timerInt`, `vantagem`, `privada`, `asCegas`, `recapFeita`, `gravandoAte` eram `let`s soltos na closure; agora moram em `const ui = {...}`, criado **uma vez** por chamada de `telaMesa(id)` (não a cada `render()`) — mesma referência sempre, só os campos dentro mudam. Motivo: assim que `telaMesa` for dividida em arquivos (`mesa-mestre.js`/`mesa-nave.js`/`mesa-combate.js`/`mesa-ficha.js`, ainda não feito), closures não atravessam módulos — estado mutável compartilhado entre "abas" precisa viver numa referência estável (`ctx.ui`) em vez de variável solta. Este passo não mudou nenhum comportamento visível, só onde cada variável mora — qualquer leitura/escrita que antes era `meuPers`/`souMestre`/etc. agora é `ui.meuPers`/`ui.souMestre`/etc.
- **`.cb-atk`** (⚔ na linha do rastreador, Mestre): agora **mira um alvo primeiro** e resolve acerto (`acerto` vs `alvo.cd`, +2 se alvo Marcado, Vantagem se alvo exposto) + dano via `aplicarDanoAlvo`, marcando `alvo_resolvido`. Ataques `bonus == null` (efeito automático / teste de resistência) continuam só postando o dado.
- **Campo tático** (`#cb-campo` no painel de Combate): grade 2D rasa — `CAMPO_LARGURA=40`m, `CAMPO_PISTAS=3` (frente/meio/fundo), `PISTA_M=1`m entre pistas (profundidade rasa), `ALCANCE_CAC=1.5`m (corpo-a-corpo), `ALCANCE_ARMA={curto:15,medio:30,longo:40}`. Cada combatente não-nave tem `c.pos = {x, lane}`. `distCombate(a,b)` = `hypot(dx, dlane*PISTA_M)`. `posInicial(ordem, tipo)` — aliados à esquerda / inimigos à direita, espalhados nas pistas; atribuído em `#cb-add-btn`, no auto-invocar e migrado em massa no início de `telaMesa`. **Janela visível**: `vistaCampo {ini,fim}` + `pctX(x)` calculados por render — campo inteiro (40 m) ou aproximado (`campoZoom`, janela `CAMPO_JANELA=12` m centrada no token selecionado / no turno atual). A grade vem de `--g1`/`--g5` inline (passo em % da janela), então o `repeating-linear-gradient` do CSS serve as duas escalas. Régua adapta o passo (1 m no zoom, 5 m no geral). **Seleção** (`tokenSel`): clique num token desenha a banda `.cb-alcance` (±`ALCANCE_CAC`), marca quem está no alcance (`.perto`, prefixo ⚔) vs fora (`.longe`, esmaecido) e lista distâncias em `.cb-distancias`. Arrastar (`.cb-token.movivel`): jogador move o seu só no turno, limite `k.deslocamento` (½ só Caído; 0 Paralisado/Congelado/**Lento**); Mestre move qualquer um; clique sem arrastar (<0,4 m) seleciona. O arraste converte px→metros pela janela visível, não pela largura total. **Alcance de arma ligado**: `alcanceDaArma(cat, pr)` → branca `ALCANCE_CAC` (1,5 m; 3 m com a chave Alcance), fogo `ALCANCE_ARMA.curto/medio/longo` (15/30/40) conforme Alcance Maior / Telescópica. No `[data-atq]` a checagem roda **antes de gastar munição**: jogador sem ninguém no alcance leva `alert` e o tiro nem acontece; o seletor só lista quem está no alcance (o Mestre vê todos, marcados com “⚠ fora de alcance”, e pode forçar — aí a resolução posta “não alcança” sem dano). `.cb-atk` mostra a distância de cada alvo e avisa fora de alcance (sem bloquear — quem conduz é o Mestre); ataques derivados de jogador carregam `alcance`. **Área por ponto de impacto**: já ligado — `aplicarEmAlvos({area:true, raio})` deixa escolher o epicentro entre quem tem `pos` e marca automaticamente todo mundo dentro do raio (`distCombate(epi, x) ≤ raio`), aliado incluído. **Amedrontado não se aproxima**: já ligado, com fonte rastreada por `origemId` (ver Modelo de dados). **Auras por raio**: já ligado — `aurasSobre(quem, oque)` filtra por `distCombate(a.fonte, quem) <= a.raio`; sem raio declarado ou sem posição dos dois lados, vale pro combate inteiro (comportamento antigo). **Empurrão**: `empurrarDe(origem, alvo, metros)` (regras.js, pura) devolve a nova posição jogando o alvo pra longe no eixo X, com clamp no campo; `aplicarEmAlvos({empurrao})` aplica de verdade no token.
- **Naves no campo tático**: naves inimigas (linha `tipo:"nave"` do rastreador) agora também ganham `c.pos={x,lane}` — `posInicial(ordem, "inimigo")` na criação (`#cb-add-btn`) e migração no início de `telaMesa` (mesmo laço que já dava posição a personagens/criaturas, estendido pra incluir naves). Recusar não impede adicionar — só não desembarca.
- **Arma de nave explosiva (área)**: `nave.armas[i]` ganhou os campos opcionais `area:true, raio:N` (as 8 armas tipo `"missil"` do catálogo `NAVES` já vêm com `raio:5`, igual escala da palavra-chave "Artilharia" de arma pessoal). - **PV/RAM/Escudo do próprio jogador visíveis na aba Combate**: `renderCombate` mostra as mesmas barras compactas da aba Ficha (`.vitais-barras.compacto`) logo no topo do painel de Combate, quando há `f`/`k` (personagem vinculado) — sem isso, quem estava lutando precisava trocar pra aba Ficha toda hora só pra conferir RAM ou escudo no meio do combate. Escudo ganhou cor própria (`.vb-fill.escudo{background:var(--chrome)}`), distinta do roxo de RAM (`sombra`), pra não confundir as duas barras. **A aba Ficha (`mesa-ficha.js`) ganhou a mesma barra de Escudo** (`data-barra="mesa-escudo"`, aparece só quando `k.escudoMax`) — antes só existia como texto solto (`🛡 escudo X/Y`) ao lado da CD, enquanto PV e RAM já eram barra; a barra de Escudo agora é EXATAMENTE o mesmo bloco (mesma classe `.vb-fill.escudo`, mesmo cálculo `escP`) nas duas abas, só o `data-barra` muda (`cb-escudo` vs `mesa-escudo`, cada aba anima a sua via `animarBarras`).
- **PV Temporário e Escudo — mecânicas DIFERENTES de propósito**: `f.pvTemp` e `f.escudoGasto` na ficha; `k.escudoMax = armadura.absorve (Escudo de Energia Pessoal = 10) + k.escudoBonus (soma de efeitos escudo_max)`, `k.escudoLivre = escudoMax − escudoGasto`. Ordem de absorção em `aplicarDanoAlvo`: imunidade a tipo → couraça por limiar → resistência adaptativa → redução (só dano físico) → **Escudo** → **PV Temporário** → corpo. A diferença entre os dois (pedida explicitamente, não é só nomenclatura): **Escudo não deixa passar excedente** — enquanto `escudoLivre > 0` no início da instância de dano, a instância INTEIRA é bloqueada, mesmo que estoure e zere o escudo (`escudo tem 10, toma 15 → os 5 de excesso NÃO chegam no corpo`; só a PRÓXIMA instância, já sem escudo, volta a valer normal). **PV Temporário deixa passar** — é só um estoque a mais de PV, o excedente segue pro corpo depois de esgotá-lo. Qualquer descanso recarrega o escudo e dissolve o PV Temporário. PV Temporário concedido por `resolve:{tipo:"pvtemp",dado,attr?,pericia?,proprio?}` (Reparo Tático, Firewall Ativo) e `resolve:{tipo:"drenar_escudos"}`, não soma (fica o maior). Escudo hoje só vem de `armadura.absorve` (Escudo de Energia Pessoal) ou de um efeito declarado `{tipo:"escudo_max",valor}` em qualquer Portador (implante/filosofia/modo/item) — capacidade genérica, sem conteúdo próprio ainda além da armadura.
- **PV máximo extra**: `f.pvMax` continua sendo o valor BRUTO salvo na ficha (setado manualmente no level-up, em `telaFicha`) — `calc()` nunca mexe nele. O que mudou: `k.pvMax = f.pvMax + k.pvMaxBonus`, onde `k.pvMaxBonus` é a soma de qualquer efeito declarado `{tipo:"pv_max",valor}` (implante/item/modo — ex. "Coração Sintético de Duplo Fluxo", +5). `k.pvMax` é o teto EFETIVO em jogo — todo clamp/exibição de PV (descanso, dano, cura, cura reflexa, ficha, cards, rastreador, painel do Mestre) foi migrado de `f.pvMax` pra `k.pvMax`/`calc(f).pvMax`; só o campo de edição do level-up (`#pvMax` em `telaFicha`) e o gate "ainda não rolou PV" continuam lendo o bruto `f.pvMax`, de propósito. Removido o implante/item que concede isso, o bônus some no próximo `calc()` (o PV atual não é reduzido à força — só passa a clampar contra o teto novo, menor, no próximo dano/cura).

Não anula nada: `FichaEfeitos.resistencias()` devolve a lista normalizada em minúsculas, e os dois pontos que já rolam teste de resistência (`aplicarEmAlvos`, no ramo `atributo/pericia + cd`, e `aplicarCondsNoAlvo` de `[data-atq]`, palavra-chave/munição com `cd`) checam `temResistencia(kAlvo, cond) || temResistencia(kAlvo, tipoDano)` e, se bater, rolam o d20 do teste com Vantagem (`Math.max(d(20),d(20))`) em vez de um dado só. Só personagens (tem `k.efeitos`); criaturas não têm equivalente ainda. "Coração Sintético de Duplo Fluxo" é o primeiro caso real: resistência a "Envenenado". Escopo intencional: só vale pra ROLAGENS de resistência/salvaguarda contra aquele dano/condição — não reduz dano já certo de acontecer (isso é `reducao_dano`) nem dá vantagem em ataques.

## Supabase

**Tabelas**: `perfis` (id, apelido, avatar_url), `personagens` (dono_id, campanha_id, nome, `dados` JSONB, publico, token_publico, atualizado_em), `campanhas` (nome, codigo, mestre_id + colunas JSONB `nave`/`mapa`/`combate`/`bestiario`/`contratos`/`faccoes`/`handout`), `campanha_membros` (campanha_id, perfil_id, posto), `mensagens` (campanha_id, autor_id, personagem_id, tipo, conteudo, `payload` JSONB), `mestre_notas` (campanha_id, texto), `conteudo` (tipo, chave, `dados` JSONB — conteúdo global do painel admin).

**Mensagens** `tipo`: `mensagem` | `rolagem` | `sistema` | `descanso`. Rolagens guardam `payload.total`, `payload.dano_total`, `crit`, `fumble`, etc.

**RPC**: `entrar_campanha({ cod })` → id da campanha.

**Realtime**: `sb.channel('mesa-<id>')` ouve INSERT em `mensagens`. Persistência de estado de combate/nave é o Mestre gravando colunas JSONB de `campanhas` (com `snapshot()` para desfazer).

**Cuidado — histórico do chat**: toda busca de `mensagens` com `limit` **sem** filtro de "a partir de agora" precisa ser `.order("criado_em", { ascending: false }).limit(N)` e **depois inverter o array** (`[...data].reverse()`) antes de usar em ordem cronológica. Buscar `ascending: true` + `limit(N)` pega as N mensagens mais **antigas**, não as mais recentes — numa campanha com mais de N mensagens (fácil de bater: cada ação de combate gera várias `sistema`), tudo recente some, sem erro nenhum. Já foi bug real (histórico do chat em `telaMesa`, backup em `fazerBackup`, linha do tempo em `painelLin`, `#abrir-diario` — os quatro corrigidos juntos). Exceção correta: `recapitular()` usa `.gt("criado_em", ultima).order(asc)` — aí `ascending: true` está certo, porque o corte já é "desde a última visita" pra frente.

**Cuidado — salvamento sem checar erro**: toda gravação em `campanhas` passa por `salvarCamp(campos, rotulo)` (em `telaMesa`) e toda gravação de `personagens.dados` por `salvarFicha(personagemId, dados, rotulo)` (módulo-level, usado por `telaFicha` e `telaMesa`) — os dois checam `error` e mostram `alert` sozinhos, devolvendo `true`/`false`. **Nunca** chamar `sb.from("campanhas").update(...)` ou `sb.from("personagens").update({ dados })` direto de novo — já foi auditoria real: mais de 55 chamadas assim (posto de nave, dano/cura, RAM, level up, descanso, recompensa, reparo de nave…) salvavam sem checar erro nenhum. Numa falha de rede/RLS o app já tinha renderizado como se tivesse dado certo, e a mudança sumia sem aviso na sincronização seguinte — a mesma categoria do bug do histórico do chat, só que na escrita em vez da leitura. `salvarFicha` tem rótulo default `"salvar a ficha"`, então é seguro chamar só com `(id, dados)` quando não há uma frase melhor.

**Cuidado — handlers "mutar tudo, salvar 1×"**: vários handlers grandes (`#cb-prox`, `[data-atq]`, `.cb-atk`) mutam `camp.combate` em vários pontos e só chamam `salvarCombate()`/`salvarCampanha()` **uma vez no final**, pra não disparar o eco do realtime no meio. Qualquer exceção lançada entre o início do handler e esse save final faz a rodada inteira (dano, condição, turno, invocação) ficar só na tela e sumir ao recarregar — sem alerta nenhum, porque o `catch` de erro do Supabase nunca é alcançado. Blocos de efeito automático/narrativo (`habsDoCombatente(...).disparar(...)`, gatilhos de criatura) devem ir em `try/catch` isolado para não arriscar o save principal.

**Storage**: upload de foto de personagem (comprimida no cliente antes do envio).

## Touch/mobile — "só aparece no :hover" é bug, não estilo

Um elemento com `opacity:0` que só vira visível em `:hover` **não existe** em celular/tablet — não há `:hover` sem mouse, e o elemento fica lá, funcional, mas impossível de descobrir. Já foi bug real duas vezes: `.card-del` (apagar personagem no Hangar) e `.m-reply` (responder mensagem no chat) ficavam em `opacity:0` de repouso. Corrigido pra um valor visível-mas-discreto em repouso (`.4`–`.55`) que intensifica no hover — nunca `0`. Mesmo raciocínio vale pro campo tático: o "modo expandido" (pistas mais altas, tokens maiores, grade de 1 m) era só `:hover`; agora `.cb-campo.perto` (ligado clicando `#cb-zoom`, funciona em qualquer dispositivo) dispara o mesmo CSS. Ao criar um controle secundário "que só aparece ao passar o mouse", sempre perguntar: como alguém sem mouse ativa isso?

O mesmo raciocínio vale pra "como alguém sem teclado FECHA isso": o painel de acessibilidade (`montarA11y()` em app.js) só tinha `Esc` (não existe em celular) e reclicar no próprio ♿ (o mesmo ícone de abrir, sem nenhuma pista visual de que também fecha) — no toque, quem abria ficava preso, sem jeito de sair sem recarregar a página. Corrigido com um padrão de modal completo: `.a11y-fundo` (overlay escurecido, `position:fixed;inset:0`, fecha ao tocar fora) atrás do painel, e um botão `✕` (`.a11y-x`) visível no canto superior direito — os três fecham pelo mesmo `fecharPainel()`, então nenhum caminho de fechar pode ficar sem os outros dois. Terceira instância do mesmo problema: descobrir "como fecho isto sem mouse/teclado" é a pergunta certa pra QUALQUER painel/overlay novo, não só os dois primeiros casos.

**Linha de botões que cresce com o conteúdo precisa quebrar em QUALQUER largura, não só no celular**: `.cb-acoes` (ações do Mestre em cada linha do rastreador) tem um `⚔N` por ataque de `ataquesDoCombatente(c)` + −5/+5/HP/🏷/cobertura/✕. O `flex-wrap:wrap` só existia dentro do `@media(max-width:720px)` — no desktop, um personagem com 7 armas empurrava a linha pra fora do card. Agora a regra base tem `flex-wrap:wrap;justify-content:flex-end` e `max-width:100%`. Mesma pergunta pra qualquer barra cujo número de itens depende de dado do jogador: o que acontece com 10 itens numa tela larga?

**Tela cheia de verdade, em vez de descontar o padding do body na conta**: `body` tem `padding:20px 14px 60px` fixo (topo do CSS) — bom pra páginas de conteúdo normais, ruim pra uma tela que precisa centralizar contra a altura EXATA do viewport (login). A primeira tentativa foi um `min-height:calc(100vh - 80px)` descontando os 80px de padding na mão — funcionava, mas ficava acoplado a um número que quebraria silenciosamente se o padding do body mudasse por qualquer outro motivo. Solução mais limpa: `shell(titulo, ...)` (app.js) liga `body.pagina-cheia` quando `titulo === "login"`; `body.pagina-cheia{padding:0}` zera o padding só nessa tela, e `.tela-login` vira um container de tela cheia de verdade — `min-height:100vh` (com `100dvh` por cima pra acompanhar a altura visível real no celular, onde a barra de endereço muda `100vh` dinamicamente) e o próprio padding lateral (`20px 14px`), sem depender de nenhum valor emprestado do body. Qualquer tela nova que precise ocupar "a tela inteira" centralizada segue o mesmo padrão: uma classe no body pra zerar o padding herdado, não uma conta de `calc()` acoplada a um número que pode mudar.

**Nav de topo (`shell()`) — menu ☰ no mobile**: com 6 elementos (logo, Hangar, Campanhas, Biblioteca, nome do usuário, SAIR) o `.menu` flex-wrap espremia/quebrava feio em telas estreitas. `.menu-links` (novo `<div>` em volta de tudo exceto logo+☰) é `display:contents` no desktop — some da equação, os filhos continuam fluindo direto como itens do `.menu`, comportamento idêntico a antes. Só abaixo de 720px o botão `#menu-burger` aparece e `.menu-links` vira um painel `display:none` → `flex column` via classe `.open`, alternado no clique do ☰ (que também vira ✕ e atualiza `aria-expanded`). Fecha sozinho ao clicar em qualquer link/botão lá dentro (senão ficava aberto por cima da tela seguinte, mesma classe de bug dos overlays sem fechar).

## Imersão (flourishes de UI)

Uma leva de detalhes puramente atmosféricos — nenhum muda regra ou resultado, só a apresentação. Todos respeitam `body.a11y-reduzir` (painel de acessibilidade) e/ou `prefers-reduced-motion:reduce`, mesma disciplina do resto do app (ver "Touch/mobile" acima e o CSS logo depois de `.m-roll.crit`).

- **Flash "código da Matrix" ao conjurar** (`efeitoMatrix()` em `ui.js`, chamado em `#conjurar` de `mesa-ficha.js` logo antes de rolar o d20): canvas fixo (`.fx-matrix`, z-index 10055) desenhando colunas de caracteres caindo por ~900ms, cor `--tech`, depois se autodestrói. Sai cedo se `body.a11y-reduzir`. Reutilizável para qualquer outro gatilho de tecnomancia no futuro — é só chamar a função, ela não sabe nada sobre scripts.
- **Zona Morta "estremece"**: o aviso `⧉ Implantes inertes` em `mesa-ficha.js` (aparece quando `k.implantesInertes`) ganhou a classe `.fx-glitch` — um tremor+RGB-split sutil e repetido via CSS puro (`@keyframes fx-glitch`), sem JS. Some com `a11y-reduzir`/`prefers-reduced-motion`.
- **Mensagens de sistema "digitam"** (`digitarTexto()` em `app.js`, chamada em `addMsg` só quando `aoVivo && m.tipo === "sistema"`): o texto entra caractere a caractere com um cursor `▊` piscando (`.digitando::after`), terminando sempre em ~500ms independente do tamanho (passo escalado por `texto.length/50`, não por um `setInterval` de intervalo fixo). **Só ao vivo** — no histórico (F5, scroll pra trás) o texto aparece pronto, senão reabrir o chat ficaria lento de propósito.
- **O d20 "rola"** (`animarRolagem()` em `app.js`, mesma regra de `aoVivo` que o item acima, só em mensagens `tipo:"rolagem"`): `.m-total` cascateia números aleatórios (70ms × 7 trocas ≈ 500ms) antes de travar no valor real (que já veio pronto do servidor — é só apresentação, não afeta a resolução nem reordena quando o Mestre pode clicar "aplicar dano"). Já passou por 300ms (rápido demais pra perceber) e 800ms (devagar demais, atrasa o chat) antes de assentar em ~500ms — se for mexer de novo, ficar perto desse valor.
- **Flash de crítico** (`flashCritico()` em `app.js`, chamado de `addMsg` junto de `animarRolagem` quando `aoVivo && m.payload?.crit` — de QUALQUER jogador, não só o próprio, ao contrário do tremor/som de `sacudir()`/`somCritico()` que só tocam pra crítico de OUTRA pessoa): `body.flash-critico::before` cobre a tela com um brilho radial `--tech` que desaparece em .5s. É além do brilho que `.m-roll.crit` já tem na própria bolha da mensagem — esse novo é pra sentir o crítico mesmo sem estar com o olho no chat naquele instante.
- **Ícone/cor por tipo de dano** (`ICONE_DANO` em `regras.js`, um mapa `tipo → {ic, cor}` sobre os mesmos 8 `TIPOS_DANO`): o ataque de arma do jogador (`[data-atq]` em `mesa-ficha.js`) agora manda `tipoDano` no payload da rolagem (`munTipo || tipoDanoArma(cat)`), e `addMsg` em `app.js` mostra um selo colorido (`.m-dano-tipo`) na mensagem quando `payload.tipoDano` existe. **Cobertura parcial de propósito**: só o ataque principal do jogador manda `tipoDano` hoje — ataques de nave/`.cb-atk` (Mestre) ainda não, então essas rolagens simplesmente não mostram o selo (degrada bem, não quebra nada).
- **Vinheta de PV baixo**: `vinhetaAtiva` (módulo-level em `app.js`) é setada só dentro do `render()` de `telaMesa` (único lugar com `f`/`k` do próprio personagem em mão) — `true` quando `f.pvAtual > 0` e `f.pvAtual / k.pvMax <= 0.25`. `shell()` é quem decide se ela aparece de fato: `body.vinheta-critica` só liga quando `titulo === "mesa" && vinhetaAtiva` — sair da mesa pra qualquer outra tela limpa sozinho, porque `shell()` roda em toda troca de tela e recalcula a condição. CSS puro depois disso: `body.vinheta-critica::after` desenha uma borda vermelha pulsando (`box-shadow: inset`, `pointer-events:none`, z-index 9990 — abaixo de tudo que é overlay de verdade).
- **Presença na mesa** (`renderPresenca()` dentro do `render()` de `telaMesa`, Supabase Realtime Presence no MESMO canal `mesa-<id>` que já existia pro chat — não abre canal novo): `.on("presence", {event:"sync"}, renderPresenca)` + `.track({uid, nome, av})` disparado no callback de `.subscribe(status => ...)` quando `status === "SUBSCRIBED"`. Renderiza chips (`.pres-chip`, avatar+nome) em `#mesa-presence`, deduplicados por `uid` (a mesma pessoa com 2 abas abertas não aparece 2×, e a SUA PRÓPRIA presença conta — abrir a mesa sozinho já mostra 1 chip com o seu nome). **Pra testar de verdade precisa de 2 CONTAS diferentes** (2 abas da mesma conta mostram só 1 chip, de propósito — é dedupe por `uid`, não por aba); numa janela anônima/outro navegador logado como outro jogador, ou pedindo pra outra pessoa abrir a mesa.
- **Banner de reconexão temático**: dirigido primariamente pelos eventos nativos do browser `window.addEventListener("offline"/"online", ...)` (`marcarSinalCaido`/`marcarSinalOk`, registrados **uma vez por entrada na mesa** — não a cada `render()`, senão empilhava um listener novo por re-render — e removidos no próximo `hashchange` via `{ once: true }`), porque o status do canal Realtime (`CHANNEL_ERROR`/`TIMED_OUT`/`CLOSED`/`SUBSCRIBED` do `.subscribe(status => ...)`, que também chama as mesmas duas funções) só percebe a queda depois de um timeout de heartbeat bem mais longo — tarde demais pra um teste rápido de "desliga o wifi, liga de novo" (foi exatamente esse teste que não mostrou nada na primeira versão, só com o canal como sinal). `#mesa-conn` mostra "⚠ SINAL PERDIDO — reconectando à matriz…" em `marcarSinalCaido`, e troca por "✅ sinal restabelecido" por ~2s em `marcarSinalOk` — mas só se `banner.dataset.caiu === "1"` (já esteve fora do ar nesta sessão), pra não mostrar "restabelecido" logo na primeira conexão.

## Camadas de z-index (CSS) — fonte recorrente de bug

`.mp-overlay` 9998 · `.ss-overlay` 9999 · `.pular-link` 10001 · **bancada** (inline em `abrirBancada`) 10020 · `.cri-overlay` 10030 · `.aviso` 10040 · `.nv-cena` 10050 · `.fx-matrix` (flash de tecnomancia) 10055 · **`.mdl-overlay`** (modais de `ui.js`) **10060** — deve ficar acima de tudo, pois exige decisão do usuário. Ao criar um overlay novo, conferir se um `confirmModal` disparado de dentro dele ainda aparece por cima. `body.vinheta-critica::after` (PV baixo) fica em 9990 e `body.flash-critico::before` (flash de crítico) em 9995, abaixo de todo overlay de verdade — de propósito, são só ambientação, nunca devem competir visualmente com um modal ou o `.aviso`.

## Testes automatizados

`tests/*.test.js`, testador embutido do Node (`node:test` + `node:assert/strict`) — zero instalação, zero `package.json`/`node_modules` novo, roda com:

```
node --test
```

**Sem caminho, de propósito**: o Node varre o projeto e roda tudo que casa com `*.test.js`. Não usar `node --test tests/` — a partir do Node 22 um diretório solto é tratado como arquivo e o runner morre com `Cannot find module '.../tests'`.

**Sem Node instalado na máquina de quem desenvolve** (não pode/não quer instalar): `.github/workflows/testes.yml` roda os mesmos testes automaticamente a cada `git push`/Pull Request, na nuvem do GitHub — zero instalação local. Resultado aparece na aba **Actions** do repositório no GitHub, e como ✓/✗ ao lado do commit. Esse é o jeito recomendado de rodar os testes quando não há Node local.

Três arquivos hoje:
- `tests/dados-jogo.test.js` — `propsArma`/`chavesDaArma`, sanidade de conteúdo que percorre `ARMAS` inteiro conferindo que toda palavra-chave cadastrada é reconhecida (pegou a própria regressão do fix de "texto duplicado nas palavras-chave"), e o mesmo tipo de sanidade para `IMPLANTES` com `.ataque` declarado (dado parseia, `kw` reconhecido).
- `tests/regras.test.js` — `calc` (ficha derivada), `dcSalvaguarda`, `aplicarCond` (empilhar dano vs. renovar estado, `origemId`), `distCombate`/`posInicial`, tipos de dano/alcance, `parseDice`, `danoCritico` (a fórmula "soma dados+bônus primeiro, multiplica depois"), a armadura anticrítica, e `k.pvMax`/`k.escudoMax` (PV máximo extra e Escudo via efeito declarado, com "Coração Sintético de Duplo Fluxo" como caso real).
- `tests/validacao.test.js` — `validar()` (criaturas.js) e `validarEfeitos()` (efeitos.js) pro select "Imune a"/"Resistente a" + sentinela `"__outro__"`, e testes diretos de `FichaEfeitos`/`Portador` pros efeitos `pv_max`/`escudo_max`/`resistencia` (unitários, sem passar por `calc()`).

**Por que dá pra testar `calc()`/`aplicarCond()`/a fórmula de crítico agora**: elas foram extraídas de `app.js` para `public/js/regras.js`, um módulo sem nenhum import de rede (só `dados-jogo.js` e `efeitos.js`, ambos igualmente limpos). Antes disso não dava: a primeira linha de `app.js` é `import { createClient } from "https://esm.sh/@supabase/supabase-js@2"`, uma URL remota que o resolvedor de módulos padrão do Node não entende, então nada do arquivo era importável em teste. `app.js` continua com o mesmo comportamento — só passou a importar essas funções de volta de `regras.js` em vez de declará-las localmente. Se for extrair mais alguma coisa de lá no futuro: confira sempre se a função usa algo do DOM (`document`), de `sb` (Supabase) ou de estado que só existe dentro de `telaMesa`/`telaFicha` — só migra o que for de fato puro (recebe dado, devolve dado).
